Julia 1.10.x · one-page guide

One course. One reproducible toolbox.

A Julia project environment tells Julia which packages belong to a project and which resolved versions to load. “Virtual environment” is useful shorthand, but this is not a virtual machine and it does not make a private copy of Julia.

Remember this The environment chooses.
The depot stores.

The files in ES313 describe the toolbox. The shared .julia folder stores the packages, binaries, and caches used to build it.

The 20-second mental model

A recipe, a lock, and a shared pantry

The first two live in the course repository and belong to this project. The third normally lives in your home folder and is shared by all your Julia projects.

1
Project.toml

The recipe

Lists the packages the course uses directly—the high-level intent of the environment.

In this repository, exact versions are not pinned here.

2
Manifest.toml

The lock

Records the complete resolved dependency graph, including exact versions and source identities.

It is generated by Julia’s package manager; do not edit it by hand.

3
~/.julia/

The shared pantry

Holds downloaded package source, binary artifacts, registries, and compiled caches.

Projects can reuse the same package files, so environments need not duplicate them.

Project.toml + Manifest.toml define this course environment → Pkg.instantiate() materializes it using the depot

What the setup scripts do for you

ES313 deliberately uses one environment at the repository root for its lecture and application notebooks.

  1. Configure or update config.jl / update.jl

    Check Julia 1.10.x, activate the repository root, and instantiate the recorded dependencies.

  2. Start start.jl

    Activates that same root environment before launching Pluto.

  3. Work Course notebooks

    Use the shared course toolbox; notebook activation is an extra safety net.

Pkg.activate(path) selects

It changes which project Julia considers active. By itself, it downloads nothing.

Pkg.instantiate() installs

It downloads missing recorded packages and artifacts, then prepares them for use.

Reproducible

Students and instructors use the same resolved package graph.

Scoped

The course dependencies take priority; another project’s lockfile does not decide what ES313 loads.

Recoverable

The version-controlled recipe and lock can reconstruct missing local package state.

Efficient

One setup serves all course notebooks, while compatible files are shared on disk.

The Julia runtime is a separate layer. An environment controls packages; it does not replace Julia itself. The ES313 scripts therefore also require Julia 1.10.x. Personal computers use Juliaup; CDN computers do not and use the system-installed C:\Program Files\Julia-1.10\bin\julia.exe instead.

Environment ≠ depot

So what exactly is .julia?

It is normally Julia’s first user depot: shared storage for package management, code loading, and user-level Julia state. It is not the ES313 environment itself.

Default location (unless JULIA_DEPOT_PATH was changed):

C:\Users\YourAccount\.julia\ /Users/YourAccount/.julia/ /home/YourAccount/.julia/

Mostly downloaded or generated state

Julia can usually fetch or rebuild these when a valid project is instantiated again.

  • packages/
  • artifacts/
  • registries/
  • compiled/
  • clones/

Potentially personal or important state

A full deletion can also remove global environments, preferences, history, configuration, development work, or notebooks saved in Pluto’s default folder.

  • environments/
  • config/startup.jl
  • dev/
  • pluto_notebooks/
  • scratchspaces/
  • prefs/
  • logs/

CDN computers do not use Juliaup. They run the system-installed Julia at C:\Program Files\Julia-1.10\bin\julia.exe. Resetting the user’s .julia folder removes package state but does not uninstall that Julia executable. On personal computers only, Juliaup stores installed Julia versions and its configuration under ~/.julia by default, so a full reset may require Juliaup repair and re-adding the 1.10 channel.

Troubleshooting, explained

Why can resetting .julia help?

The folder is not inherently a problem. A reset is useful only when local depot state has become incomplete, damaged, or unusable.

Interrupted transfer

Failed transfers or damaged downloaded state can leave Pkg unable to complete or use an installation.

Broken generated state

A compiled cache can become stale or damaged after a failed update or system change.

Access problem

Incorrect permissions, a lock, or problematic configuration can prevent Pkg from reading or writing.

The rationale for a clean reset

The course’s Project.toml and Manifest.toml remain safely in the ES313 folder. Removing suspect local depot state gives Pkg.instantiate() an empty workspace in which to download the recorded dependencies again and rebuild caches. In other words: keep the blueprint, rebuild the local warehouse.

Use the smallest reset first

Close Julia and Pluto. Confirm that you are using Julia 1.10.x, use a stable open network, and retry the setup. If the error explicitly concerns precompilation, renaming only .julia/compiled/v1.10 is a much narrower reset; Julia will rebuild it.

To check which depot your Julia actually uses, start Julia exactly as described for your platform and enter this at the julia> prompt:

first(DEPOT_PATH)

Rename a cache
Narrow and reversible

Best when the error clearly identifies generated cache state.

Rename all .julia
Broad, last-resort reset

Affects every Julia project for your account and may also remove Juliaup’s installed runtimes.

Delete immediately
Not recommended

You lose the option to recover configuration, environments, history, Pluto notebooks, or work from dev/.

If a full reset is genuinely needed

  1. Close every Julia, Pluto, and VS Code Julia process.
  2. Rename .julia to a backup name instead of deleting it. Preserve anything in pluto_notebooks/ or dev/, and keep the backup until everything works.
  3. CDN computer: do not install or invoke Juliaup. Continue with C:\Program Files\Julia-1.10\bin\julia.exe; it remains installed after a depot reset.
  4. Personal computer: if juliaup no longer runs, reinstall or repair it first; then run juliaup add 1.10.
  5. Repeat the course’s complete Getting started (do this once) sequence on a stable network.
  6. Test start.jl. Do not copy generated folders such as packages/, artifacts/, compiled/, or registries/ back.
  7. Recover only files you know you created or customized, such as notebooks in pluto_notebooks/, work in dev/, or config/startup.jl.

A depot reset will not fix the wrong Julia version, a proxy or offline network, an incorrect Git path, damaged files in the ES313 repository, or an error in notebook code. It also triggers a large re-download and fresh precompilation, so it can take time.
